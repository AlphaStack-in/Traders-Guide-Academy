# Research: performance-email-digest

**What:** Build signal outcome tracking (auto-resolve open signals against target/SL via live price data) and a weekly performance email digest for subscribers (win rate, P&L in points and rupees, best/worst trade) sent via Resend on a Sunday-evening Vercel Cron.

**When:** 2026-08-24

---

## Summary

- **Risk:** Medium
- **Approach:** Two-phase build. Phase 1 adds a new cron route that polls live prices and auto-resolves OPEN signals. Phase 2 adds a weekly digest cron that aggregates closed signals per subscriber, computes metrics (reusing `signal-metrics.ts` helpers), resolves lot sizes via the existing DhanInstrument table, renders an HTML email, and sends via the already-installed Resend SDK. New Prisma models for `DigestSendLog` (audit/dedup) and schema additions for subscriber email-preference (unsubscribe). Follows the established `isAuthorizedCronRequest` + `CRON_SECRET` cron pattern exactly.
- **Effort:** Significant

## Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| **Lot size unavailable for expired signals** -- DhanInstrument is a daily cache that only holds current contracts. Past-expiry signals can't resolve lot size for rupee P&L. | High | Snapshot `lotSize` onto the Signal model at creation time (new nullable field `lotSize Int?`), or maintain a separate historical lot-size lookup table. Snapshotting is simpler and more reliable. |
| **Live price source dependency** -- Phase 1 auto-resolve needs a reliable, free/low-cost live price API. Dhan's market-quote API requires an active access token from a connected subscriber. | Medium | Use one designated "system" broker connection for price polling (admin's own Dhan token), or use a free index-price source (NSE website scrape / a public API). Alternatively, skip auto-resolve entirely and keep manual close (admin-driven) as the only path -- this defers Phase 1 but unblocks Phase 2. |
| **Email deliverability** -- Resend requires a verified sending domain. The current `EMAIL_FROM_ADDRESS` placeholder (`noreply@tga-placeholder.app`) won't deliver to real inboxes. | Medium | Must configure a real domain in Resend before going live. Dev/staging can use Resend's sandbox or the existing dev-simulation fallback. |
| **Subscriber email coverage** -- `Subscriber.email` is nullable (`String?`). Subscribers without an email address won't receive digests. | Low | Filter to subscribers where `email IS NOT NULL` and `emailDigestOptOut = false`. Log skipped subscribers in the cron response. |
| **SignalStatus enum change** -- Adding `EXPIRED` to the `SignalStatus` enum requires a Prisma migration and is a schema-level change that touches every query filtering by status. | Low | `EXPIRED` is additive-only (no existing rows use it), so existing queries are unaffected unless they use exhaustive switch/match. Grep for `SignalStatus` usage to confirm. |
| **Vercel Cron 60s timeout** -- Both crons (especially digest with N subscribers x email sends) must complete within Vercel's function timeout. | Medium | Batch email sends. If subscriber count is large, consider Vercel's `maxDuration` increase (up to 300s on Pro) or split into batched invocations. For the near term (small subscriber base), 60s should suffice. |
| **Duplicate digest sends** -- Without dedup tracking, a retry or re-invocation could send the same digest twice. | Low | `DigestSendLog` model records `(subscriberId, weekStartDate)` with a unique constraint. Check before sending; skip if already sent. |

## Open Questions

1. **Live price source for auto-resolve?**
   - Options: (A) Dhan market-quote API via a system broker token, (B) Free NSE/BSE data scrape, (C) Skip auto-resolve -- keep manual close only
   - Recommendation: (C) for MVP. Auto-resolve is valuable but introduces a runtime dependency on a live data source. The digest can work with the existing manual-close flow (signals already transition to TARGET_HIT / SL_HIT / CLOSED_MANUAL via admin actions). Phase 1 can be deferred or built as a separate follow-up.

2. **Lot size snapshotting vs. historical lookup?**
   - Options: (A) Add `lotSize Int?` to Signal, snapshot at creation, (B) Keep a `DhanInstrumentHistory` table
   - Recommendation: (A) -- simpler, no extra table, and the lot size is known at signal creation time. Backfill existing signals with a one-time script querying the current DhanInstrument cache (only works for non-expired contracts; older ones get null / default).

3. **Subscriber tier filtering -- SubscriberPlan has only PREMIUM today.**
   - Options: (A) Gate on `plan = PREMIUM`, (B) Gate on a new `isActive` / `subscriptionExpiresAt` field
   - Recommendation: (A) for now since there's only one plan. Add `subscriptionExpiresAt DateTime?` when a paid-tier model is actually implemented. For the digest, filter on `plan = PREMIUM AND email IS NOT NULL AND emailDigestOptOut = false`.

4. **Unsubscribe mechanism?**
   - Options: (A) Signed token in email link that flips `emailDigestOptOut`, (B) Account settings toggle
   - Recommendation: Both. The email includes an HMAC-signed one-click unsubscribe link (compliance requirement). The account page also surfaces the preference.

5. **Week boundary: Sunday-to-Saturday or Monday-to-Sunday?**
   - Recommendation: Monday 00:00 IST to Sunday 23:59 IST (standard Indian trading week). Cron fires Sunday evening IST (e.g. 18:00 IST = 12:30 UTC).
